# 目标

做一个自媒体 agent（项目名 zimeiti-ai）：**把「选题 → 图文创作 → 双平台发布」的每周重复劳动交给 agent，用户只在关键节点做确认**，先把内容运营的时间成本降下来，再逐步叠加数据回流与获客能力，最终长成可商业化的订阅 SaaS。

问题组合与主次：**没时间运营（首要）> 创作瓶颈 > 获客转化难**。现状是零散工具（ChatGPT 写文案 + 平台后台手动发），链路不打通、无沉淀。

双形态定位（与知识库原方案一致）：Web 工作台（人主导）与 24h 托管（agent 主导 + 人审批）共用同一套执行图，首版以最小闭环先验证托管循环的可行性。

商业模式：先自用打磨（自己是第一个用户），跑通后按订阅 SaaS（多租户）商业化。

# 范围

**首版（MVP）能力**——选题 → 图文创作 → 双平台发布的最小闭环：

- 账号画像（小红书 + 公众号两个账号的定位/风格/受众配置）
- 选题辅助（热点/竞品信息输入 → 选题卡产出，人工挑选）
- 图文创作（小红书笔记 + 公众号文章草稿，含封面文案）
- 发布执行（Playwright 自动化 + 发布前 HITL + 读回对账）
- 托管循环骨架（定时/事件触发的最小自治循环，审批点外全部自动）

**明确不在首版**（进 ROADMAP）：数据回流与账号画像自动更新、获客侧（评论区截流、微信 IM、客服 crew）、短视频、多租户与计费（架构预留计量埋点）。

**内容形态**：图文（小红书笔记 + 公众号文章）。短视频后续迭代。

**技术栈**（已锁定，细节归各变更 Design Doc）：LangGraph 主干 + deepagents 创作段 + LiteLLM + MCP + FastAPI + Next.js + Playwright + Postgres/pgvector。

# 非目标

- 不自研底层模型
- 不做通用 coding agent
- 不做平台方官方 API 的替代
- 首版不做：短视频、获客侧（评论区截流/微信 IM/客服）、归因回流与画像自动更新、多租户/计费的完整实现（仅预留埋点）

# 验收示例

- **A1 选题产出**：Given 账号画像与热点/竞品输入，When 触发选题，Then 产出若干选题卡（含推荐理由），由人工挑选进入创作
- **A2 图文创作**：Given 选定选题与账号画像，When 触发创作，Then 产出小红书笔记草稿与公众号文章草稿（含封面文案），风格符合画像
- **A3 发布 HITL**：Given 待发布草稿，When 用户在审批点确认，Then 内容发布到小红书与公众号
- **A4 未核实不报成功**：Given 发布动作已执行但读回对账失败，Then 结果标记为 unverified 而非成功
- **A5 托管审批边界**：Given 托管模式运行中，When agent 尝试未获审批的发布动作，Then 动作被阻断并等待人工确认
- **A6 全链路闭环**：Given 上述各环节，When 走完一轮，Then 用户每周运营时间显著低于全手工基线（时间节省为北极星指标）

# 约束与不变量

- 发布前必须人工确认（HITL），未确认不执行任何对外发布动作
- 平台凭证加密存储（KMS 或等价），不落明文、不入日志、不入代码库
- 平台自动化操作内置风控护栏（频控/操作白名单/高危平台标注），禁止伪造登录态
- 出站内容必须通过 fail-closed 合规审查，审查为系统级强制而非 prompt 约束
- 技术栈按知识库锁定项执行，替换需变更决策记录

# 决策

- 项目名：zimeiti-ai（弃用 content-agent 占位名）
- 问题主次：时间 > 创作 > 获客（北极星 = 时间节省，产量/增长/获客为二级指标）
- 主形态：双形态并行（工作台 + 托管，共用同一套执行图）
- 内容形态：图文起步；首发平台：小红书 + 公众号
- 商业化路径：订阅 SaaS（多租户），首版自用验证后开放
- 差异化依据：Easel + xiaobei 两大开源参考（不从零摸索）、多 agent 工程经验、自媒体业务经验、工作流+托管+获客的组合拳定位（现有工具都只做一半）
- 时机依据：模型能力成熟 + skills/MCP 生态就绪 + 个人窗口期
